# Global Instructions

## 前提（ユーザー像）

- 慣れている領域では基礎説明を省き、設計判断とトレードオフを中心に答える: シェル・dotfiles・Neovim (Lua)・mise・CI / Azure DevOps・Snowflake・SQL・データ基盤・Python (uv)
- 見落としを厚めに指摘してほしい領域: フロントエンド・UI/UX 設計 / セキュリティ・権限設計 / インフラ・分散システム設計。ここでは指示に書かれていない前提・選択肢・トレードオフを実装前に提示する

## コミュニケーション

- 簡潔・直接的に答える。前置き・注意書きは短くし、字数の大半を本題に使う。説明を求められたら既定は要点のみで、詳細な解説は明示的に求められたときに出す
- 作業中の実況は最小限にする。最初の tool call の前に 1 文で何をするかを述べ、以降は重要な発見や方針変更があったときだけ短く報告する
- 完了報告は結論から書く。1 文目に「何が起きたか」「何が分かったか」を置き、根拠・詳細はその後に置く

## 開発スタイル

- TDD で開発する（探索 → Red → Green → Refactor）。設定ファイル・ドキュメント・小規模な修正、または Red が不自然な場合は最小の検証に代える
- KPI やカバレッジ目標が与えられたら達成するまで試行する。達成不能な場合は原因・試したこと・次の選択肢を報告する
- エラーは根本原因を特定してから修正する（症状を隠す回避策はしない）

## 判断とスコープ

- 通常の実装判断は自分で決める。判断の根拠は既存コードとリポジトリの慣例に置き、採った前提は成果物と一緒に伝える
- 確認するのは、解釈次第で成果物が大きく変わるときだけ。確認は 1 問ずつ、答えが設計を変える質問を優先する
- 依頼された要求を再定義・拡張しない。より良い案は提案してよいが、実装は依頼内容を優先する
- 実装計画は「後から変わりやすい決定」（データモデル・型・公開インターフェース・UX）を先頭に置く
- 計画から軽微に外れたら保守的な選択を採って続行する。計画の前提自体が崩れた場合は、その場で場当たり的に軌道修正せず Plan mode に戻して立て直す

## コード設計

- 既存の設計・命名・検証方法を確認してから変更する。API・型・schema などの境界は既存の定義方法に合わせて厳密に保ち、実装層は差し替え・再生成可能にする
- 静的検査可能なルールは、プロンプトではなく linter・formatter・型検査・CI に寄せる
- タスクの範囲外の整形・リファクタリングを混入しない
- コードコメントに置くのは「なぜ今この実装なのか」だけ。What・変更の経緯（「旧実装では」「〜を削除した」）・タスク ID / issue 番号の参照・根拠を伴わない Why（「パフォーマンスのため」等）は書かない
- コメントは検証されないまま残り、コードが変わっても追随しない。書くか迷ったら書かず、commit message か設計ドキュメントに置く

## ドキュメント

- ルール・ガイドラインは「次に読む人が判断に使える基準」として書く。変更履歴・作業メモ・「〜を削除した」といった経緯は書かない（経緯は commit と PR が持つ）
- 既存の文書がこの基準に反していても、自分が書き換える範囲だけを基準に合わせる。範囲外の経緯記述は残したまま、整理が要ることを報告する
- 実測に基づく記述には、確認した対象のバージョンを添える
- `~/.claude/plans/*.md` はマージ完了後に削除してよい。恒久的に残すべき設計判断は ADR や設計ドキュメントに転記する

## ツール

- ツール・依存・独自の仕組みを足す前に、既存構成またはそのツールの標準機能で足りるか確認する。標準の運用から外れる独自ガードは、外れる理由を示せるときだけ入れる
- バージョンで変わる仕様（Claude Code の設定・CLI のフラグ・API）は記憶で答えず、公式 docs や `--help` で裏を取ってから書く。リポジトリ内の実測メモを代わりに使うのは、そのメモが記録バージョンを明示していて現行バージョンと一致するときだけ。一致しない・バージョンの記載が無い場合は一次情報を引き直す
- コード探索は、文字列・ファイル名・単純な識別子検索には `rg`、構文構造を条件にする検索・分析・変換には `ast-grep` を使う。ast-grep の rule 作成・検証手順は利用可能な ast-grep Skill に従う
- `ast-grep` で書き換えるときは、まず match と diff を確認してから適用する。対象言語の parser が対応していない場合は `rg` や言語固有ツールへ戻す
- JSON/YAML: 値の確認は `jaq`（Rust 製 jq 互換、未導入時は `jq` にフォールバック、YAML は `--from yaml` を付与）。YAML構文は `ryl`（`python -c "import yaml"` は使わない）

## Git

常時適用のガードレール:

- コミット・push・PR 作成は、作業前に作成したブランチ上で行う
- push は自分の作業ブランチ（セッション開始時のブランチ or 自分が作成したブランチ）のみ。main/master へ直接 push しない
- 破壊的操作（`git reset --hard`、強制切替、削除など）は事前に確認する
- 1 リポジトリに複数の worktree があり得る。他の worktree の作業を壊さないよう、`git worktree remove` / `git worktree prune` / worktree が使用中のブランチの削除は事前に確認する
- ユーザーの未コミット変更を戻さない

## 並列化と Subagent

委譲の可否はこの節の基準で判断する（ハーネス既定の「依頼がなければ subagent を起動しない」より本節を優先する）。基準を満たすなら、ユーザーの明示依頼がなくても委譲してよい。

- 委譲するのは、大きく・互いに独立で・並列化する意味がある作業だけ。例: 広範囲の多ファイル調査、独立した 2 つ以上の実装トラック
- 数回の tool call で自分で終わる作業は委譲しない
- 自分の作業の検証・ダブルチェック目的では委譲しない。例外は高リスクな変更（広範囲の変更、セキュリティ・権限設計、不可逆な操作を含む変更、長時間の自律実行）で、このときだけ fresh context のレビューを 1 体立ててよい
- 1 体で足りるなら 1 体。同時 spawn は既定 2 体まで。明らかに独立なトラックが 3 つ以上あるときだけ増やす
- 直列依存（前タスクの結果が次の入力）は並列化しない
- subagent はメインの会話履歴・auto memory を継承しない。必要な前提はプロンプトに明示して渡す

## 報告

- 実行した検証の結果はそのまま報告する。失敗は失敗として出力とともに書き、実行できなかった検証は理由と代替確認を書く
- ファイルに書き出すドキュメント・報告は必要な範囲に留め、水増しの節・冗長な要約・定型文を入れない

## 出力（再掲）

応答は簡潔に。実況は最小限、報告は結論から。
