# Global Instructions

## 前提（ユーザー像）

- 自走できる領域（説明は簡潔でよい）: シェル・dotfiles・Neovim (Lua)・mise / Azure DevOps・CI
- 自走できるが実装は Claude Code に任せることが多い領域（設計判断は簡潔でよいが、生成コードは自己レビュー水準で提示する）: Snowflake・SQL・データ基盤 / Python・データ処理 (uv)
- 見落としを厚めに指摘してほしい領域: フロントエンド・UI/UX 設計 / セキュリティ・権限設計 / インフラ・分散システム設計
- 3 番目の領域では、指示に書かれていない前提・選択肢・トレードオフを実装前に提示する

## コミュニケーション

- 簡潔・直接的に答える。

## 開発スタイル

- TDD で開発する（探索 → Red → Green → Refactoring）。ただし、設定ファイル・ドキュメント・小規模な修正、または Red が不自然な場合は最小の検証を優先する。
- KPI やカバレッジ目標が与えられたら達成するまで試行する。達成不能な場合は原因・試したこと・次の選択肢を報告する。
- エラーが発生した場合は根本原因を特定してから修正する（症状を隠す回避策はしない）。

## 不確実性の解消

成果物の質は、モデルの能力より「要求に残る不確実性をどれだけ潰せたか」で決まる。実装前に unknown を減らす。

- 実装前に「まだ決まっていない点」を洗い出す。設計・データ構造・外部インターフェース・UX を変える論点は、仮定で進めず先に確認する
- 不明瞭な指示は質問して明確にする。確認は 1 問ずつ、答えが設計を変える質問を優先する
- 「前提（ユーザー像）」の不慣れ領域では、指示に現れていない前提・見落としを先に列挙する
- 説明より参照実装。既存コード・類似実装を根拠として示す
- 実装計画は「後から変わりやすい決定」（データモデル・型・公開インターフェース・UX）を先頭に置く
- 実装中に計画から外れたら、保守的な選択を採り、逸脱と理由を記録して続行する。記録は `$TMPDIR` 等の追跡対象外に置き、リポジトリに残さない
- 計画の前提が崩れるほど大きく脱線した（軽微な逸脱の範囲を超える）場合は、その場で場当たり的に軌道修正せず、Plan mode に戻って計画を立て直す

## Plan ファイルの扱い

- `~/.claude/plans/*.md` はマージ完了後に削除してよい
- 恒久的に残すべき設計判断は ADR や設計ドキュメントに転記する。plan ファイル自体では管理しない

## コード設計

- 関心の分離を保つ。状態とロジックを分離する
- API・型・schema などの境界は、既存の定義方法に合わせて厳密に保つ。実装層は差し替え・再生成可能にする
- 静的検査可能なルールは、プロンプトではなく linter・formatter・型検査・CI に寄せる
- 既存の設計・命名・検証方法を確認してから変更する
- タスクの範囲外の整形・リファクタリングを混入しない
- コードコメントは Why が非自明な場合のみ書く（What は書かない）

## ツール

- ツール・依存を追加する前に、既存構成で代替できるか確認する
- JSON/YAML: 値の確認は `jaq`（Rust 製 jq 互換、未導入時は `jq` にフォールバック、YAML は `--from yaml` を付与）。YAML構文は `ryl`（`python -c "import yaml"` は使わない）

## Git

常時適用のガードレール（手順は `git-flow` skill を参照）:

- コミット・push・PR 作成は、作業前に作成したブランチ上で行う
- push は自分の作業ブランチ（セッション開始時のブランチ or 自分が作成したブランチ）のみ。main/master へ直接 push しない
- 破壊的操作（`git reset --hard`、強制切替、削除など）は事前に確認する
- ユーザーの未コミット変更を戻さない

## 並列化と Subagent

委譲の可否はこの節の基準で判断する（ハーネス既定の「依頼がなければ subagent を起動しない」より本節を優先する）。基準を満たすなら、ユーザーの明示依頼がなくても委譲してよい。

- 委譲するのは、大きく・互いに独立で・並列化する意味がある作業だけ。例: 広範囲の多ファイル調査、独立した 2 つ以上の実装トラック
- 数回の tool call で自分で終わる作業は委譲しない
- 自分の作業の検証・ダブルチェック目的では委譲しない
- 1 体で足りるなら 1 体。同時 spawn は既定 2 体まで。明らかに独立なトラックが 3 つ以上あるときだけ増やす
- 直列依存（前タスクの結果が次の入力）は並列化しない
- subagent はメインの会話履歴・auto memory を継承しない。必要な前提はプロンプトに明示して渡す

## 検証と報告

- 変更後は対象に合った最小十分な検証を実行する
- 検証できない場合は、理由と代替確認を報告する
- ファイルに書き出すドキュメント・報告は必要な範囲に留め、水増しの節・冗長な要約・定型文を入れない。ドキュメントの構成・文体は `doc-writing` skill を参照する

## スキル作成

- 配置先: 複数 repo で再利用するなら `~/.claude/skills/`（実体は dotfiles の `claude/skills/`。symlink 元を直接編集する）、特定 repo 固有なら `<repo>/.claude/skills/`、判断不能ならユーザーに確認する
- 後から移動するとパス参照が壊れやすい。配置先が不明な場合は必ず事前確認し、既存 skill を移動・分割・統合する前に影響範囲を確認する
- 作成・編集の手順自体は `skill-creator` skill を呼ぶ
