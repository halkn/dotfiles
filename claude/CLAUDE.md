# Global Instructions

## 前提（ユーザー像）

- 慣れている領域では基礎説明を省き、設計判断とトレードオフを中心に答える: シェル・dotfiles・Neovim (Lua)・mise・CI / Azure DevOps・Snowflake・SQL・データ基盤・Python (uv)
- 見落としを厚めに指摘してほしい領域: フロントエンド・UI/UX 設計 / セキュリティ・権限設計 / インフラ・分散システム設計。ここでは指示に無い前提・選択肢・トレードオフを実装前に提示する

## 開発

- TDD（探索 → Red → Green → Refactor）。設定・ドキュメント・小規模な修正や Red が不自然なときは最小の検証に代える
- エラーは根本原因を直す。症状を隠す回避策は取らない
- API・型・schema の境界は既存の定義方法で厳密に保つ
- 静的検査できるルールは linter・formatter・型検査・CI に寄せる
- タスクの範囲外の整形・リファクタリングを混ぜない
- 開発ツールと版の固定は、言語の標準とデファクト（uv・bun・go の `toolchain` / `tool`）に合わせ、mise に寄せない。clone した人と CI が言語の手順だけで再現できるように
- コードコメントは「なぜこの実装か」だけ。ファイル冒頭・節の見出しのコメントには、そのファイルが何を扱うかを書いてよい。What の言い換え・変更の経緯・issue 番号・版付きの調査メモは commit message に置く。ツールの公式 docs や `--help` に書いてあることはどこにも書き写さない

## 判断とスコープ

- 曖昧な要求は非破壊・狭い側で進め、採らなかった解釈は「関連」として添える。破壊的な解釈・範囲の拡張・依頼の一部を落とす解釈を採るときだけ承認を取る
- 確認の答えに依存しない作業は、答えを待たずに先に進める
- 実装計画は後から変わりやすい決定（データモデル・型・公開インターフェース・UX）を先頭に置く
- 計画から軽微に外れたら保守的な選択を採って続行する。計画の前提が崩れたら、場当たりに直さず、止めて崩れた前提を報告する
- ツール・依存・独自ガードを足す・乗り換える前に、既存構成と標準機能で足りるかに加えて、外す側を他のツール・plugin・agent が暗黙に前提にしていないか、入れる側を agent が使い慣れているか、戻すときの手順と条件を確かめる
- issue・Work Item を作業の前提にするときは、着手前に最新のコード・docs・他の未完了の issue・Work Item と照らし、書かれた後の変化・範囲の重なり・実装済みでないかを確かめる。前提が崩れていたら記述どおりに進めず、食い違いと代わりの設計を報告する（記述の方針への異論は対象外）

## ドキュメント

- 次に読む人が判断に使える基準として書く。経緯は commit と PR に任せる。範囲外の経緯記述は直さず、整理が要ると報告する
- 整理を頼まれたら、差分の小ささより置き場所の正しさと重複の解消を優先する
- 設計ドキュメントにはツールの挙動の実測（版・値・回数）を書かず、そこから決まる基準と採らない選択肢だけを書く。実測は commit と PR に残す。古い実測を次の agent が事実として守り続けるため
- 対象を限定した方針はリポジトリの設計ドキュメント（`docs/` など）に置き、AGENTS.md / CLAUDE.md からは「何を触る前に読むか」で参照する（`@import` しない）

## 仕様の確認

- 版で変わる仕様（Claude Code の設定・CLI のフラグ・API）を名指しするときは、公式 docs か `--help` を引いてから書く。commit や PR に残した実測で代えられるのは、記録された版が現行と一致するときだけ
- ツールの設定を変える・新しい版に追従するときは、変更の前に公式 docs の該当ページを読み、変更点に加えて、docs から見て直すべき点と、新機能で置き換えられる既存の設定も挙げる。`--help` とリリースノートからは変わった箇所しか分からない
- `allowedDomains` にある docs は `curl` で取得して `rg` で原文を確かめる。それ以外は WebFetch（tool が無いセッションでは `web-fetch` agent）
  - Bash に `allowed_domains` を付けない（`strictAllowlist` で拒否される）。allowlist に無いホストへの通信が要るコマンドは、`!` での実行を頼む
- 仕様に由来する表や定数（プロトコルの符号表など）は記憶で書かず、一次資料か既存の実装から取り出して照合する。記憶の誤りは一部の項目にだけ混ざり、見た目では気付けない

## 環境

- 検索は `rg`、構文を条件にする検索・変換は `ast-grep`。値の確認は `jq` / `yq`、YAML 構文は `ryl`
  - 呼出しの引数・形を複数箇所で変える書き換えは、Edit の繰り返しや `sed` ではなく `ast-grep run -p '<pattern>' -r '<rewrite>' -l <lang>` で行う。`-U` の前に一度 `-U` 無しで一致を確かめる。テキスト置換は改行や入れ子の呼出しで漏れる
- Bash は作業ディレクトリの中で動かす。作業ディレクトリの外のパスを書いた Bash と、sandbox の外で動くコマンドの追えない展開は、auto モードでも `blockReadsOutsideWorkingDirectories` の確認になる
  - ファイルの書き換えは Edit / Write tool で行う。ハーネスは auto モードで Bash での書き換えを勧めるが、それが確認の主な原因になっている
  - 一時ファイルはハーネスの指示どおり scratchpad に置き、Read / Write / Edit tool で扱う
  - `~/.claude` の skills・plugins・agents・commands・rules は Read tool で読む。Bash で読むと確認になる
  - 他のリポジトリでは `~/.claude/CLAUDE.md`・`settings.json` を Read でも読めない。CLAUDE.md は会話に読み込まれた本文を使い、settings.json が要るなら halkn/dotfiles のセッションに引き継ぐ
  - 上流のソースは `gh api -H 'Accept: application/vnd.github.raw' 'repos/<o>/<r>/contents/<path>?ref=<版>'` で読み、`--jq` は付けない（応答が JSON でない）。多くのファイルを読む・`rg` で探すときは、`gh repo clone <o>/<r> .scratch/<テーマ>/<r> -- --depth 1` で作業木の中に clone する
  - 手元にある他のリポジトリの clone（`~/repos` の下）は、読む前に `/add-dir` を頼む。`~/.local/share` のインストール先は Bash で読み、確認を受け入れる
- sandbox・`blockReadsOutsideWorkingDirectories` の拒否と依存の取得（`mise install` など）は、`/add-dir` か `!` での実行をユーザーに頼む。ただし PATH に載るバイナリやプラグインを置く data ディレクトリ（`~/.local/share` など）は `/add-dir` に出さない（sandbox の書込まで開く）。hook・`pre-push` の拒否は、メッセージに従って自分で直す

## Git

- リモートのホストは push 先の URL で判断する。GitHub は `gh`、Azure DevOps は `az repos` で操作する
- PR の依頼は、そのブランチへの以後の push を含む
- push は自分の作業ブランチ（セッション開始時のブランチか自分が作成したブランチ）だけに行う。push 済みのブランチは履歴を書き換えず commit を積む
- `gh` の全サブコマンド（読取を含む）と git の push・fetch・clone・ls-remote は、他のコマンドとパイプ・`;`・`&&`・ループで繋がず単体で打ち、出力は `--jq` で絞る。`git pull` は `git fetch` と `git merge` に分ける
  - `gh` は sandbox の外で動き、追えない引数は確認になる。`--jq` は `.[] | "\(.a)\t\(.b)"` のような文字列補間の形にし、配列の構築（`[.a, .b] | @tsv`・`[.a] | join(…)`）・スライス（`.sha[0:7]`）・`select(.a=="b")` を入れない
- merge・main/master を変える操作・ガードの変更（branch protection / ruleset / branch policy・default branch・公開範囲・alias）は、GitHub・Azure DevOps・ローカルのどれでも、対象を名指しされたときだけ行う
- 他の worktree では書込・switch・削除をしない。別のセッションが並行して作業している

## 報告

- 実行できなかった検証には、代わりに確認したことを添える
- 版で変わる仕様を調べて報告するときは、主張ごとに出典（URL・`--help`・ソースのパスと ref）と確認した版を添え、確かめられなかった点を分けて書く。後で引く結果は PR 本文に移す
- 自分で観測できない変更（TUI・キー操作・自分の実行環境では動かせないもの）は、手で確認する手順を番号付きで添える
