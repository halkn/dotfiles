# Global Instructions

## 前提（ユーザー像）

- 慣れている領域では基礎説明を省き、設計判断とトレードオフを中心に答える: シェル・dotfiles・Neovim (Lua)・mise・CI / Azure DevOps・Snowflake・SQL・データ基盤・Python (uv)
- 見落としを厚めに指摘してほしい領域: フロントエンド・UI/UX 設計 / セキュリティ・権限設計 / インフラ・分散システム設計。ここでは指示に書かれていない前提・選択肢・トレードオフを実装前に提示する

## 開発スタイル

- TDD で開発する（探索 → Red → Green → Refactor）。設定ファイル・ドキュメント・小規模な修正、または Red が不自然な場合は最小の検証に代える
- KPI やカバレッジ目標が与えられたら達成するまで試行する。達成不能なら、試したことと次の選択肢を出す
- エラーは根本原因を特定してから修正する（症状を隠す回避策はしない）

## 判断とスコープ

- 曖昧な要求は非破壊・狭い側を既定の作業仮説にする。採らなかった解釈は捨てず「関連」として区別を付けて添える。破壊的な解釈や範囲の拡張を採るときだけ承認を取る
- ドキュメントの整理を頼まれたときは、差分の小ささより「何をどこに書くべきか」と重複の解消を優先する
- 確認は 1 問ずつ、答えが設計を変える質問を優先する
- 実装計画は「後から変わりやすい決定」（データモデル・型・公開インターフェース・UX）を先頭に置く
- 計画から軽微に外れたら保守的な選択を採って続行する。計画の前提自体が崩れた場合は、その場で場当たり的に軌道修正せず Plan mode に戻して立て直す

## コード設計

- 既存の設計・命名・検証方法を確認してから変更する。API・型・schema などの境界は既存の定義方法に合わせて厳密に保ち、実装層は差し替え・再生成可能にする
- 静的検査可能なルールは、プロンプトではなく linter・formatter・型検査・CI に寄せる
- タスクの範囲外の整形・リファクタリングを混入しない
- コードコメントに置くのは「なぜ今この実装なのか」だけ。実装の途中に挟む注釈は 1 行に収める。ファイル冒頭・セクション見出しのコメントは対象外で、そのファイルが何を対象に何を見るかを書いてよい。コメントは検証されないまま残りコードが変わっても追随しないので、迷ったら書かず commit message か設計ドキュメントに置く
- commit 前に、追加したコメントを 1 つずつ次に照らして消す: ツールの公式ドキュメントにある説明・言語やツールの既定動作から自明なこと・What の言い換え・変更の経緯（「旧実装では」「〜を削除した」）・タスク ID / issue 番号の参照・根拠を伴わない Why（「パフォーマンスのため」等）・バージョンを伴う調査メモ（今の実装の理由になるものは設計ドキュメントへ移し、ならないものは捨てる）

## ドキュメント

- ルール・ガイドラインは「次に読む人が判断に使える基準」として書く。変更履歴・作業メモ・「〜を削除した」といった経緯は書かない（経緯は commit と PR が持つ）
- 既存の文書がこの基準に反していても、自分が書き換える範囲だけを基準に合わせる。範囲外の経緯記述は残したまま、整理が要ることを報告する
- 設定や実装の理由として実測結果を書くときは、確認した対象のバージョンを添える。規約や手順の指示には添えない（指示は版が変わったら書き直すもので、版の記録は判断に使われない）
- 対象を限定した設計方針・判断基準は、リポジトリの設計ドキュメント（例: `docs/`）に置き、AGENTS.md / CLAUDE.md から「何を触る前に読むか」を添えて参照する。`@import` で取り込まない（起動時に全文が読み込まれる）。実測は今の設計の理由になるものだけを「決定と理由」として残す
- `.claude/rules/` は使わない: path-scoped rule が読み込まれるのは Read tool が一致するファイルを読んだときだけで、bash で読むと発火せずエラーも出ない（Claude Code 2.1.275 の docs で確認）
- skill は複数のリポジトリで繰り返し使う手順（workflow）に使い、特定のリポジトリの設計や実測記録は置かない。一度ロードされた本文は以降のターンに残り続けるため
- `~/.claude/plans/*.md` はマージ完了後に削除してよい。恒久的に残すべき設計判断は ADR や設計ドキュメントに転記する

## ツール

- ツール・依存・独自の仕組みを足す前に、既存構成またはそのツールの標準機能で足りるか確認する。標準の運用から外れる独自ガードは、外れる理由を示せるときだけ入れる
- バージョンで変わる仕様（Claude Code の設定・CLI のフラグ・API）は記憶で答えない。**設定キー・フラグ・既定値を名指しする文を書く時点で**、公式 docs か `--help` を引いてから書く。記憶と一致していることは根拠にならない。同じセッションで同じ版を引き済みなら引き直さない
- 公式 docs や `--help` の代わりにリポジトリ内の実測メモを使えるのは、そのメモが記録バージョンを明示していて現行バージョンと一致するときだけ。一致しない・バージョンの記載が無い場合は一次情報を引き直す
- 文字列・ファイル名・単純な識別子検索は `rg`、構文構造を条件にする検索・分析・変換は `ast-grep`（rule 作成・検証手順は `ast-grep:ast-grep` Skill に従う）
- `ast-grep` で書き換えるときは、まず match と diff を確認してから適用する。対象言語の parser が対応していない場合は `rg` や言語固有ツールへ戻す
- git のネットワーク系（`push` / `fetch` / `pull` / `clone` / `ls-remote`）と `gh` は 1 行 1 コマンドで実行し、パイプ・`&&`・`;`・`$(...)` でつながない。sandbox の除外が単純コマンドにしか効かないため。出力はツール自身のオプション（`--json` / `--jq`、`-n`）で絞る
- JSON/YAML: 値の確認は JSON が `jq`、YAML が `yq`。YAML 構文は `ryl`（`python -c "import yaml"` は使わない）

## Git

常時適用のガードレール:

- コミット・push・PR 作成は、作業前に作成したブランチ上で行う
- push は自分の作業ブランチ（セッション開始時のブランチ or 自分が作成したブランチ）のみ。main/master へ直接 push しない
- 破壊的操作（`git reset --hard`、強制切替、削除など）は事前に確認する
- 1 リポジトリに複数の worktree があり得る。他の worktree の作業を壊さないよう、`git worktree remove` / `git worktree prune` / worktree が使用中のブランチの削除は事前に確認する
- ユーザーの未コミット変更を戻さない

## 並列化と Subagent

委譲の可否はこの節の基準で判断する（ハーネス既定の「依頼がなければ subagent を起動しない」より本節を優先する）。基準を満たすなら、ユーザーの明示依頼がなくても委譲してよい。

軸は **context 分断と実行コストを上回る利得があるか**。利得は、中間出力（検索結果・ログ・広範囲の読取）を隔離して結論だけ受け取る・独立した作業を同時に走らせて所要時間を縮める・tool を絞った状態や安いモデルで走らせる、のいずれか。示せないなら委譲しない。

- 委譲しない: 数回の tool call で終わる作業、結論より過程の共有が要る作業、直列依存の作業、自分の作業の検証・ダブルチェック目的（例外はセキュリティ / 権限設計・不可逆な操作・長時間の自律実行を含む変更で、このときだけ fresh context のレビューを 1 体立ててよい）
- 並列度は独立トラックの数で決める
- 独立 session を並べる仕組み（background session・cross-session messaging・agent teams・workflow）は既定では使わず、必要と判断したらユーザーに諮る
- worktree isolation は、2 体以上が同じ repo へ同時に書き込むとき・親が編集中のファイルに触るときだけ使う。成果は commit / branch 経由で受け取る

## 報告

- 実行できなかった検証は、理由と代わりに何を確認したかを書く
- ファイルに書き出すドキュメント・報告は必要な範囲に留め、水増しの節・冗長な要約・定型文を入れない
