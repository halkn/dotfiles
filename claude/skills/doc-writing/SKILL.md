# ドキュメント作成

## 適用範囲

この skill は、linter が検査できない**構成と文体**を扱う。見出しの記法・行長・リスト記号のような機械検査可能な規約は `rumdl`（`mise run lint` / `rumdl check <file>`）に任せ、ここでは重複させない。

対象は、一定期間参照・保守される開発文書（Wiki・Design Doc・ADR・Runbook・README・API ドキュメント・運用手順・技術調査結果）である。GitHub Issue・Azure Boards work item・PR 本文・コミットメッセージは、状態を追跡する作業レコードであり対象外とする。境界の判断は「Work item との境界」を参照する。

## 書き始める前に決めること

順序が重要。読者と種類が決まる前に本文を書き始めると、後から全面的に書き直すことになる。

1. **対象読者を明示する** — 誰が、何を既に知っている前提で読むのか。必ず言語化する。ただし成果物に書くのは Wiki の冒頭だけで、Design Doc・ADR・Runbook ではテンプレートに読者欄を足さず、書き手のメモに留める
1. **文書の種類を 1 つ選ぶ** — 下記から選ぶ。1 つの文書に複数の種類を混ぜない
1. **規模を決める** — Design Doc 系は「文書規模の判定」に従う
1. **既存ドキュメントの構造・文体を確認する** — 同じリポジトリに先行する文書があれば、そちらの見出し構成・語調・用語に合わせる。この skill の規約はデフォルトであって、リポジトリ固有の慣習が優先される。ただし既存文書の冗長さや重複は踏襲しない

## 文書の種類

### 専用の型がある 4 種別

| 種類 | 使うタイミング | テンプレート | 詳細ガイド |
|------|--------------|------------|-----------|
| Wiki | 手順・FAQ など、繰り返し参照される非決定情報 | `assets/wiki-page-template.md` | `references/wiki-guide.md` |
| Design Doc（別名: RFC、Proposal、Tech Spec） | 実装前に設計とトレードオフの合意を得たい | `assets/design-doc-template.md` | `references/design-doc-guide.md` |
| ADR | 個別の技術判断 1 件と、その文脈を短く記録する | `assets/adr-template.md` | `references/adr-guide.md` |
| Runbook | 特定のアラート・インシデントへの対応手順 | `assets/runbook-template.md` | `references/runbook-guide.md` |

迷ったときの目安。未来の設計合意 → Design Doc / 過去の個別判断の記録 → ADR / 決まった障害対応の手順 → Runbook / それ以外の繰り返し参照情報 → Wiki。

Azure DevOps Wiki に掲載する場合は `references/azure-devops-wiki-guide.md` も参照する。

### それ以外の文書（Diátaxis）

README・チュートリアル・リファレンス・一般の説明文は、上の 4 種別の型を当てず、次の 4 分類で構成を決める。分類は読者の状態で分かれる。**学習中か作業中か**、**実践か理解か**の 2 軸。混在させると、作業中の読者は背景説明に阻まれ、理解したい読者は手順の羅列から Why を読み取れなくなる。どちらの読者も目的を果たせない。

| 種類 | 読者の状態 | 書き方 |
|------|-----------|--------|
| チュートリアル | 初めて触る。学習したい | 手順を省略しない。動く状態まで必ず導く。選択肢を並べず 1 本道にする |
| 手順（How-to） | 目的が決まっていて作業中 | ゴールと前提を先に示し、順序付きリストで書く。網羅より最短経路 |
| リファレンス | 特定の項目を調べに来た | 網羅性と検索性を優先する。表・見出しで引けるようにする。手順を混ぜない |
| 説明（Explanation） | 背景を理解したい | Why と設計判断に集中する。手順を混ぜない |

判断に迷ったら「読者はこの文書を読みながら手を動かすか」を問う。動かすならチュートリアルか手順、動かさないならリファレンスか説明。

## 文書規模の判定

この判定は Design Doc にだけ適用する。小規模な内容に Full Design Doc のテンプレートを適用しないための判定であり、**ADR・Runbook・Wiki は対象外**。それらは種別自体が分量の制約を持つ（ADR は 1 決定 1 ページ、Runbook は 1 アラート 1 本）ため、種別固有の制約を優先する。

局所的で可逆な判断を記録したい依頼は、設計メモではなく ADR が適することが多い。「決めた理由を後から辿れるようにしたい」なら ADR を選び、テンプレートの各節を最小限の分量で埋める。

| 規模 | 適用条件 | 出力 |
|------|---------|------|
| 設計メモ | 単一の局所的な判断・可逆性が高い・1 ページ未満で説明できる。かつ**記録として残すことが目的ではない**（目的なら ADR を選ぶ） | テンプレートを使わず、決定と理由だけを散文で書く |
| Mini Design Doc | 単一チーム内の変更・複数の実装要素がある・代替案や制約の説明が要る | テンプレートの必須節（概要・Goals/Non-Goals・設計・代替案）だけを使う |
| Full Design Doc | 複数チームに影響する / API・データモデル・権限境界を変更する / 移行やロールバックが要る / 高コストまたは不可逆 / 複数の代替案を詳細に比較する | テンプレートの全節を検討する |

## 作業モード

依頼がどのモードかを最初に判定する。モードを取り違えると、短縮を頼まれてレビューコメントだけを返す、レビューを頼まれて全文を書き換える、といった失敗になる。

### 作成

種類 → 規模 → テンプレート → 詳細ガイドの順に決め、「文章作成原則」に従って書く。最後に「圧縮工程」を実行する。

情報が足りない場合は、それらしい内容を創作しない。対応は不足しているものの階層で決める。

- **骨格が決まらない**（種別・対象読者・スコープが不明）: 書き始めず、質問をまとめて一度に行う
- **骨格は決まり、個別の値が欠けている**（URL・しきい値・権限名など）: 質問で止まらず、`<要確認: 何を確認すべきか>` の形でその位置に明示し、末尾に要確認箇所を一覧化して進める

### 短縮・改稿

既存文書の事実・決定・手順・制約を保持したまま、冗長性と重複を削除する。

**完成した改稿版そのものを出力する。** 指摘のリストで終わらせない。削除の判断基準は「圧縮工程」に従う。原文にない技術的事実を追加しない。

保持するのは内容であり、見出しと節構成は文章作成原則に従って変更してよい。種別ガイドが要求する構造要素（Wiki の WHO/WHAT/WHERE/WHY など）が原文に欠けている場合は、**原文の事実から再構成できる範囲でのみ**補う。原文になく再構成もできない情報は補わず、`<要確認: ...>` として残す。

原文にないプラットフォーム固有の記法（`[[_TOC_]]` など）を新規に追加しない。

### レビュー

依頼されていない限り、全文を書き直さない。指摘は次の形式で出す。

```text
問題箇所
影響
最小限の修正案
```

手順は `references/review-checklist.md` に従う。指摘には `[Must]` / `[Want]` / `[Nit]` の重大度を付け、`[Nit]` だけを理由に差し戻さない。

## 文章作成原則

- 読者が必要とする結論、決定または操作を先に示す
- 1 文書 1 目的、1 節 1 トピック、1 段落 1 主張とする
- 判断理由と因果関係は散文で説明する
- 独立した条件は箇条書きにする
- 順序のある作業は番号付きリストにする
- 同一軸の比較は表にする
- 同じ主張を言い換えて繰り返さない
- 判断に影響しない一般論を追加しない
- 形式を満たすためだけの節を追加しない
- 主語や対象は、曖昧になる場合だけ明示する
- 未確認事項を確認済みの事実として書かない
- 既存文書からは用語と確認済みの事実を踏襲する。冗長さと重複は踏襲しない

情報の優先順位と、文体の詳細はそれぞれ `references/information-design.md` と `references/ja-writing-style.md` を参照する。

## 圧縮工程

作成または改稿の後に、一度だけ実行する。次を削除する。

- 本文の内容を予告するだけの導入
- 本文直後の再要約
- 同じ主張の言い換え
- 判断に影響しない一般論
- 読者が容易に補える中間説明
- 空の節
- 形式を満たすためだけの「該当なし」
- テンプレート由来の不要な定型表現

残す段落は、少なくとも次のいずれかを含む必要がある。含まないなら削る。

事実 / 決定 / 根拠 / 手順 / 制約 / リスク / 未解決事項

### 一般論かどうかの判定

その文書固有の対象（このジョブ・このサービス・この判断）に紐づく記述は残す。分野一般に当てはまり、対象を差し替えても成り立つ記述は削る。

- 残す: 「このバッチは各種レポートの生成に使われるため、失敗を放置すると業務に影響する」
- 削る: 「近年、データ基盤の重要性はますます高まっており、バッチ処理の安定運用は不可欠である」

Wiki の WHY（`references/wiki-guide.md`）は前者で書く。WHY を書くこと自体は、一般論を書いてよい理由にならない。

### 削除しないもの

圧縮工程でも次は残す。これらは未完成の印ではなく、確認すべき事項が特定されているという情報である。

- `<要確認: ...>` 形式のプレースホルダと、末尾の要確認箇所の一覧。項目が 1 つでも一覧を残す。本文中のプレースホルダと末尾一覧が同じ内容を指すのは重複とみなさない
- 判断に必要な条件・例外・閾値

## テンプレートの扱い

テンプレートは必須項目の一覧ではなく、候補となる構造である。該当しない項目のために節を作らない。空の節も「該当なし」も残さない。

例えば Design Doc の横断的関心事（セキュリティ・権限・可観測性・運用・コスト・データ保持・移行・ロールバック）は、その設計判断に影響する項目だけを書く。

## Work item との境界

次の内容は、GitHub Issue や Azure Boards work item ではなく、開発文書への分離を検討する。

- 複数の作業項目へ影響する設計判断
- Issue 完了後も長期的に参照する技術的背景
- 複数の合理的な代替案の比較
- API・データモデル・権限境界の変更
- 移行またはロールバック計画
- 複数チームでの合意が必要な内容

分離した文書は work item からリンクする。同じ説明を開発文書と work item の両方へ複製しない。局所的で短く、その作業だけで完結する判断は work item 本文に残してよい。
