# レビューチェックリスト

`doc-writing/SKILL.md` の詳細ガイド。新規作成時のセルフチェックと、既存文書のレビューの双方から参照する。上から順に確認し、欠けている項目を該当箇所付きで指摘する。

## 1. 共通

- [ ] 1 文書 1 目的が守られている（複数の目的が混在していないか）
- [ ] 文書の規模が内容に見合っている（小さな判断に Full Design Doc の型を当てていないか）
- [ ] コードや設定から自動的にわかる情報（全カラムの列挙、パラメータの網羅等）を重複して書き写していないか。書き写しは参照リンクへの置き換えや削除を提案する
- [ ] work item に残すべき作業レコードが混入していないか（`SKILL.md` の「Work item との境界」）

## 2. 冗長性

作成・改稿の直後と、レビュー時の両方で確認する。

- [ ] 本文の内容を予告するだけの導入がないか
- [ ] 本文直後の再要約がないか
- [ ] 同じ主張が言い換えで繰り返されていないか
- [ ] 判断に影響しない一般論が混じっていないか
- [ ] 読者が容易に補える中間説明を書いていないか
- [ ] 空の節がないか
- [ ] 形式を満たすためだけの「該当なし」が残っていないか
- [ ] テンプレート由来の定型表現やプレースホルダが残っていないか（`<要確認: ...>` と末尾の要確認箇所は例外。`SKILL.md` の「削除しないもの」を参照）
- [ ] 各段落が「事実・決定・根拠・手順・制約・リスク・未解決事項」のいずれかを含むか

## 3. 種別固有の構成

### Wiki

- [ ] 冒頭で WHO/WHAT/WHERE/WHY が示されている（`wiki-guide.md`）
- [ ] 既存の他ページと内容が重複していないか

### Design Doc

- [ ] Goals/Non-Goals が計測可能に書かれている（曖昧語で済ませていないか）
- [ ] 代替案（Alternatives Considered）が 1 つ以上あり、利点・欠点・不採用理由が揃っている
- [ ] 横断的関心事のうち、この設計判断に実際に影響するものが書かれている

### ADR

- [ ] Status（Proposed/Accepted/Superseded）が明記されている
- [ ] Context/Decision/Consequences が揃っている
- [ ] 却下した代替案とその理由が書かれている
- [ ] 決定が変わった場合、本文を書き換えず新レコード + superseded の形になっているか

### Runbook

- [ ] 対象アラート・シナリオが一行で特定できる
- [ ] エスカレーション先・前提権限が明記されている
- [ ] Symptom → Diagnosis → Mitigation → 復旧確認 → Permanent fix の順序になっている
- [ ] 副作用のあるコマンドに警告が添えられている
- [ ] 「状況に応じて対応する」のような読者に判断を委ねる記述が残っていないか
- [ ] 複数シナリオが 1 つの Runbook に混在していないか

## 4. 文体

`ja-writing-style.md` に従う。

- [ ] 説明部・仕様部の区別に応じたルールが適用されているか
- [ ] 一段落一トピックになっているか（説明部）
- [ ] 日本語の文章が 1 行 1 段落で書かれているか
- [ ] 推量表現を根拠なく断定に変えていないか
- [ ] 受動態でなく行為者主体で書かれているか
- [ ] LLM 的表現（予告・総括型、姿勢宣言、空虚な形容・動詞、根拠のない緩和、接続の型）が使われていないか
- [ ] 見出しが具体的で、内容を特定できるか

## 指摘の出し方

- 該当箇所を引用してから、問題点と最小限の修正案をセットで示す
- 指示なく無断で全文を書き換えない。改善案は提案として示し、適用は依頼者の判断に委ねる。ただし依頼が「短縮・改稿」であれば、完成した改稿版そのものを出力する
- 削除も改善である。陳腐化・重複した記述に気づいたら、追記の提案だけでなく削除や参照リンクへの置き換えも選択肢として示す
- Wiki で重複が疑われる場合は、単一の真実源の候補と、統合または非推奨化の進め方を添える
- 原文にない技術的事実を、改善案の中に紛れ込ませない

## 指摘の重大度

| ラベル | 意味 |
|--------|------|
| **[Must]** | 誤り・誤解を招く記述・重大な欠落。修正が必須 |
| **[Want]** | 読者体験を大きく改善する提案。対応を推奨 |
| **[Nit]** | 表記・文体の細かい指摘 |

迷う場合は「将来の意思決定や読者の解釈を誤らせる欠落か」を基準にする。誤らせるなら `[Must]`（例: 代替案が皆無、目標が非計測的）、読みやすさや運用上の利便性にとどまるなら `[Want]` とする。

レビューの目的は完璧な文書ではなく、改善の速いサイクルである。`[Nit]` だけを理由に差し戻しを求めない。文書を今より良くする指摘をまず示し、残りは次回の更新に回してよい、という温度感で指摘量を調整する。
