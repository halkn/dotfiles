# 設計ドキュメント

このリポジトリを変更する人と agent のための設計方針。変更する前に、触る対象の doc を読む。どの対象にどの doc が対応するかは、agent が常に読み込む [AGENTS.md](../AGENTS.md) の「Design docs」にある。

## doc の書き方

`docs/` の各 doc は、個々の設定や実装の理由を並べず、設定を選ぶときの原則・基準を書く。設定を足したら、次の順に扱いを決める。

1. 既存の原則から導ける: 何も書かない
1. ツールの挙動でしか決まらない: 挙動そのもの（版・実測の値・回数）は書かず、そこから決まる基準か採らない選択肢を、その doc の「決定と理由」に 1 行で書く。検査できる前提はテストか lint にする。測った証拠は commit と PR に残す。記述と実際の挙動が食い違ったら、公式 docs を読むか測り直してから設定を変える
1. それ以外で、読み手が理由を問いそうなもの: 先に原則を足し、そこから導けるようにする

挙動の記録を doc に置かないのは、ツールの更新ごとに古くなり、毎回読む agent が古い記録を事実として守り続けるため。基準は挙動が変わっても読み直すまで正しく、崩れたらテストか実際の失敗で気付ける。

好みで決める設定（配色・表示など）は書かない。どの文書でも、ツールの公式ドキュメントや `--help` に書いてあること、コードや設定ファイルを読めば分かること（設定値の列挙）、変更の経緯（commit と PR が持つ）は書かない。

## 何をどこに書くか

| 書く内容 | 置き場所 |
| --- | --- |
| セットアップと日常の操作 | リポジトリ直下の `README.md` |
| agent 向けの検証手順と規約 | `AGENTS.md` |
| 複数のファイルにまたがる原則・判断基準、コメントを書けないファイル（JSON）の設定を導く原則 | `docs/` |
| 1 つのファイルで完結する理由・制約 | そのファイルの該当箇所のコメント |
| コマンドの使い方 | `--help` |

`README.md` は英語、`AGENTS.md` と `docs/` は日本語で書く。
