# 設計ドキュメント

このリポジトリを変更する人と agent のための設計方針。変更する前に、触る対象の doc を読む。

| 触る対象 | doc |
| --- | --- |
| `mise.toml`・`mise-tasks/`・`.config/mise/`、ツールの追加 | [mise.md](mise.md) |
| `.zshenv`・`.config/zsh/`・`bin/`・`.config/herdr/`・`test/` | [shell.md](shell.md) |
| `.config/nvim/` | [neovim.md](neovim.md) |
| `claude/`・`.claude/` | [claude-code.md](claude-code.md) |
| 上記以外（`.config/git/`・その他の `.config/*`・`.github/`） | 専用の doc は無い。ファイルにコメントがあればそれに従う。git の `pre-push` hook は [claude-code.md](claude-code.md) の「hook の基準」（main への push を止める 4 つの層）も読む |

## doc の書き方

`docs/` の各 doc は、個々の設定や実装の理由を並べず、設定を選ぶときの原則・基準を書く。設定を足したら、次の順に扱いを決める。

1. 既存の原則から導ける: 何も書かない
1. 実測でしか決まらない（ツールの挙動に依存する）: その doc の「決定と理由」に、確認したバージョンを添えて書く。記述と実際の挙動が食い違ったら、公式 docs を読むか測り直してから設定を変える
1. それ以外で、読み手が理由を問いそうなもの: 先に原則を足し、そこから導けるようにする

好みで決める設定（配色・表示など）は書かない。どの文書でも、ツールの公式ドキュメントや `--help` に書いてあること、コードを読めば分かること、変更の経緯（commit と PR が持つ）は書かない。

## 何をどこに書くか

| 書く内容 | 置き場所 |
| --- | --- |
| セットアップと日常の操作 | リポジトリ直下の `README.md` |
| agent 向けの検証手順と規約 | `AGENTS.md` |
| 複数のファイルにまたがる原則・判断基準、コメントを書けないファイル（JSON）の設定を導く原則 | `docs/` |
| 1 つのファイルで完結する理由・制約 | そのファイルの該当箇所のコメント |
| コマンドの使い方 | `--help` |

`README.md` は英語、`AGENTS.md` と `docs/` は日本語、コードコメントは英語で書く。
